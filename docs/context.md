# 对话机制：上下文、缓存、队列

## 消息怎么组装

每次请求的消息数组按固定顺序拼装（`src/chat/assemble.ts`）：

```
[system]  基础人设 + 个性指令 + 记忆 + 跨对话参考   ← 稳定段，轻易不变
[system]  滚动摘要（仅超预算的旧对话才有）          ← 变更频率低
[历史消息] 预算内全量（每轮只在尾部追加）           ← 追加式增长
```

- 上下文预算默认 16k tokens，设置中可选 8k – 128k
- 预算内发送**全量历史**，不按条数截断
- 超出预算的旧消息从头裁剪；被裁掉的消息累积到 8 条以上时，后台压缩成要点摘要（≤300 字，与旧摘要合并），下次请求以摘要形式携带——压缩替代丢弃
- 开启联网搜索的请求按官方要求在历史 assistant 消息上回传 `reasoning_content`

## 为什么要"追加式"

DeepSeek 平台有自动前缀缓存：相邻请求前缀相同的部分自动命中，命中部分按未命中价的约 1/10 计费（以 `deepseek-flash` 为例：输入未命中 1 元/百万 tokens，命中 0.02 元起，[官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)）。追加式增长让除尾部外的整个前缀都能命中。

代价：滚动摘要更新会改变中段内容，该轮缓存失效一次。在意成本可以把预算调大，基本不触发压缩。

## 深度思考与联网搜索

- **深度思考**：请求的 `thinking` 参数控制（`deepseek-flash` 模型），流式返回 `reasoning_content`，界面折叠展示
- **联网搜索**：声明官方服务端工具 `deepseek_web_search`，搜索与上下文拼接在 DeepSeek 服务端完成（不进提示词，因此不影响前缀缓存）。回答引用通过 `annotations` 返回，消息下方展示来源
- 两个开关同时打开 = 官方的「深度思考搜索」
- 是否真的发起搜索由模型判断；搜索按查询词条计费（5 元/千次）

## 会话标题

首次对话请求开启官方 `title` 能力，由 DeepSeek 生成会话标题；未返回时回退为用户首条消息的前 40 字。

## 发送队列与中止

- 回复进行中发送的新消息**立即显示**并入队，当前回复完成后自动按序续发（跨会话也成立）
- 输入栏上方显示「⏳ N 条排队中」
- 停止按钮：中断当前流式回复（已生成部分保留，标注"已停止生成"），同时**取消全部排队消息**；被取消的消息保留在历史里，之后发送的新消息仍会携带它们作为上下文
- 请求出错（如余额不足）同样清空队列，避免排队消息挨个失败刷屏
